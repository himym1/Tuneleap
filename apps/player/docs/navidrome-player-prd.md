---

## 1. 执行摘要

Navidrome Player 是一个面向个人音乐库用户的跨平台客户端，基于 Flutter 构建，主要服务于自托管 Navidrome/Subsonic 生态。产品目标是从“可播放”演进为“可长期日常使用”，最终具备桌面与移动端一致体验、稳定后台播放能力、离线能力和高可定制性。

当前项目已完成 Phase 1，并已落地 Phase 2/3/4 的一部分能力：主导航、音乐库、搜索、全屏播放器、歌词、下载、多服务器、快捷键等已具备基础实现；后续重点转向稳定性、交互细节与高级能力补强。

本 PRD 统一定义产品目标、功能模块、用户流程、验收标准、非功能约束与阶段交付边界，作为后续设计、开发、测试和验收的单一依据。

## 2. 产品目标与成功标准

### 2.1 产品目标

1. 让用户在 3 分钟内完成首次连接并开始播放。
2. 提供稳定的日常听歌闭环：找歌、播放、管理队列、收藏、播放列表。
3. 在 Android 与 macOS 上保持一致核心体验，并对桌面场景提供增强能力。
4. 在网络不稳定或离线场景下保持可用性（Phase 4）。

### 2.2 成功指标（KPI）

1. 首次连接成功率 ≥ 95%（登录后 `ping` 成功）。
2. 首次播放成功率 ≥ 98%（点击歌曲后 3 秒内进入播放）。
3. 后台播放稳定性：30 分钟连续后台播放不中断率 ≥ 99%。
4. 搜索响应时间 P95 < 800ms（服务端可用前提下）。
5. 崩溃率 < 0.3%（按会话计）。
6. 离线播放命中率（有下载资源时）≥ 99%。

## 3. 用户画像

### 3.1 主要用户：自托管音乐用户

- 角色：Navidrome 服务拥有者或家庭成员。
- 目标：快速访问个人音乐库，稳定播放，跨设备一致。
- 痛点：网页端体验一般、移动端与桌面端操作不一致、网络波动影响体验。
- 技术水平：中等（了解服务器地址与账号配置）。

### 3.2 次要用户：重度听歌与收藏管理用户

- 角色：每天高频听歌、依赖播放队列和播放列表。
- 目标：快速检索、队列管理、收藏同步、播放历史统计。
- 痛点：列表管理繁琐、查找成本高、缺少离线支持。
- 技术水平：中高。

## 6. 核心用户流程

### 6.1 首次使用流程

1. 打开应用进入 `Login`。
2. 输入服务器地址、用户名、密码。
3. 系统执行 `ping` 验证。
4. 成功后进入 `Home` 并加载最近添加专辑。
5. 点击专辑进入详情并播放歌曲。

### 6.2 日常听歌流程

1. 在 `Home/Library/Search` 找到歌曲。
2. 单击播放或加入队列。
3. 在 `MiniPlayer/Player` 控制播放、切歌、循环、随机。
4. 在队列页调整顺序，收藏歌曲或添加到播放列表。

### 6.3 离线流程（Phase 4）

1. 用户下载歌曲/专辑。
2. 网络不可用时自动优先播放本地缓存。
3. 恢复网络后继续服务端同步（收藏/播放记录等）。

## 7. 功能需求清单（含实现状态）

> 状态定义：`已实现`、`部分实现`、`未实现`。

### 7.1 账号与服务器连接

- 状态：`已实现（单服务器）`。
- 需求：
  1. 支持输入 `serverUrl`、`username`、`password` 并保存本地。
  2. 支持连接测试与错误提示（网络异常、认证失败、URL 无效）。
  3. 自动读取历史配置并尝试自动登录。
- 验收标准：
  1. 配置保存后重启应用仍可读取。
  2. `ping` 失败时给出可读错误信息。
  3. 自动登录失败时回退登录页，不崩溃。

### 7.2 首页发现（最近添加）

- 状态：`已实现`。
- 需求：
  1. 展示最近添加专辑网格。
  2. 下拉刷新。
  3. 点击专辑可查看歌曲列表并播放。
- 验收标准：
  1. 首屏可见 20 张专辑（可配置）。
  2. 加载失败时显示错误态与重试入口。

### 7.3 音乐库浏览（艺术家/专辑）

- 状态：`已实现（基础浏览能力）`。
- 需求：
  1. 已支持艺术家、专辑、歌曲三类浏览。
  2. 已支持从艺术家进入专辑列表、从专辑进入详情。
  3. 后续可继续补充分页、更多排序与状态保留。
- 验收标准：
  1. 可从艺术家进入其专辑列表。
  2. 专辑与歌曲列表可正常浏览和播放。

### 7.4 搜索

- 状态：`已实现（基础搜索主链路）`。
- 需求：
  1. 基于 `search3` 同时搜索 Artist/Album/Song。
  2. 输入防抖（建议 300ms）。
  3. 分组结果展示并支持播放/跳转。
- 验收标准：
  1. 空关键词不发请求。
  2. 连续输入时通过防抖减少请求抖动。
  3. 搜索结果可按歌曲/专辑/艺术家筛选。

### 7.5 播放核心能力（Audio Engine）

- 状态：`已实现（基础主链路）`。
- 已有能力：
  1. 单曲/列表播放。
  2. 播放、暂停、上一首、下一首。
  3. 随机与循环模式（off/all/one）。
  4. 音量与播放速度控制。
- 待补强：
  1. 队列持久化。
  2. 播放失败自动跳过策略（可配置）。
  3. 更完整的错误可视化反馈。
- 验收标准：
  1. 播放完成后按模式正确衔接下一行为。
  2. 切歌时 UI 状态与实际播放状态一致。

### 7.6 后台播放与系统媒体控制

- 状态：`部分实现`（已接入 `audio_handler.dart` 与主播放链路，仍需补强平台稳定性）。
- 需求：
  1. 进入后台持续播放。
  2. 通知栏/锁屏控制（Play/Pause/Next/Previous/Seek）。
  3. 系统媒体键联动。
- 验收标准：
  1. 后台 30 分钟播放不中断。
  2. 系统控制操作后，应用内状态 1 秒内一致。

### 7.7 全屏播放页

- 状态：`已实现（基础交互已可用）`。
- 需求：
  1. 大封面、歌曲信息、进度条、完整控制。
  2. 歌词、队列、倍速、音量等辅助面板。
  3. 显示播放来源与队列入口。
- 验收标准：
  1. 进度拖拽可用，误差 < 1 秒。
  2. 歌词与当前播放位置保持基本同步。

### 7.8 播放队列管理

- 状态：`部分实现`（已具备查看、重排、移除、下一首等基础能力）。
- 需求：
  1. 查看当前队列与当前播放项。
  2. 拖拽排序、移除项、下一首播放。
  3. 清空队列（保留当前播放可选）。
- 验收标准：
  1. 队列变更立即生效且不打断当前播放。
  2. 删除当前曲目时按策略自动切换下一曲。

### 7.9 播放列表管理

- 状态：`部分实现`（已支持列表读取、创建、删除）。
- 需求：
  1. 查看播放列表列表与基础详情。
  2. 创建、删除播放列表。
  3. 后续补齐重命名、添加/移除歌曲。
- 验收标准：
  1. 创建/删除后 UI 与服务端列表一致。
  2. 后续批量操作需补充明确反馈。

### 7.10 收藏与同步

- 状态：`部分实现`（已有收藏页与交互入口）。
- 需求：
  1. Song/Album/Artist 收藏与取消收藏。
  2. 收藏状态在列表和详情页一致展示。
  3. 启动或进入页面时读取远端状态。
- 验收标准：
  1. 歌曲收藏已具备乐观更新基础。
  2. 失败回滚与统一状态源仍需补强。

### 7.11 Scrobble 播放记录

- 状态：`部分实现`（已在播放链路中自动上报）。
- 需求：
  1. 播放达到阈值后自动上报（>50% 或 >4 分钟）。
  2. 避免重复上报。
  3. 后续补充断网缓存待上报任务，恢复后重试。
- 验收标准：
  1. 每首歌曲单次播放只上报一次。
  2. 重试机制不会阻塞主线程和播放链路。

### 7.12 歌词系统

- 状态：`部分实现`（已具备歌词展示与同步高亮基础）。
- 需求：
  1. 获取并展示歌词（Subsonic API）。
  2. 播放同步滚动与高亮。
  3. 后续补充点击某行跳转播放位置。
- 验收标准：
  1. 无歌词场景有优雅空态。
  2. 同步歌词可跟随播放位置高亮。

### 7.13 动态主题与视觉增强

- 状态：`部分实现`（已在播放器使用封面取色）。
- 需求：
  1. 封面取色生成播放页动态配色。
  2. 深浅色主题增强（对比度、层级、动效统一）。
  3. 页面过渡与加载动画。
- 验收标准：
  1. 播放页可基于封面取色生成主题色。
  2. 后续扩展到全局主题与更细致动效。

### 7.14 设置中心

- 状态：`部分实现`。
- 需求：
  1. 当前服务器信息与退出登录。
  2. 主题与外观设置（system/light/dark）。
  3. 音质、缓存统计、关于信息。
  4. 多服务器管理入口。
- 验收标准：
  1. 主题与音质设置可持久化并即时生效。
  2. 退出等关键操作可完成主链路。

### 7.15 离线下载与离线播放

- 状态：`部分实现`（已支持单曲下载与离线回退播放）。
- 需求：
  1. 歌曲下载任务管理与下载列表展示。
  2. 本地文件存储与已完成任务持久化。
  3. 离线优先读取与空间管理。
- 验收标准：
  1. 离线状态可优先播放已下载内容。
  2. 暂停/续传/批量下载等高级能力待补。

### 7.16 音质选择与均衡器

- 状态：`部分实现`（音质选择已实现，均衡器未实现）。
- 需求：
  1. 音质档位（原始/高/中/低），映射 `maxBitRate`。
  2. 均衡器预设 + 自定义（平台能力允许范围内）。
- 验收标准：
  1. 音质设置对后续请求生效。
  2. 不支持均衡器的平台有清晰降级提示。

### 7.17 桌面增强（快捷键）

- 状态：`部分实现`（基础快捷键已接入）。
- 需求：
  1. `Space` 播放/暂停，`Cmd+←/→` 上下曲，`Cmd+F` 搜索，`Cmd+1~5` 导航。
  2. 焦点策略明确，避免输入框抢键冲突。
- 验收标准：
  1. 常用快捷键在桌面主界面可稳定触发。
  2. 输入态下不误触全局播放控制。

### 7.18 多服务器支持

- 状态：`部分实现`（增删改切换已具备）。
- 需求：
  1. 维护多服务器配置（增删改查）。
  2. 一键切换当前服务器并刷新上下文数据。
  3. 后续扩展每个服务器独立保存用户偏好和缓存策略。
- 验收标准：
  1. 当前活跃服务器在全局可见。
  2. 缓存与偏好完全隔离仍需补强。

## 8. API 与数据契约

### 8.1 已接入 API（SubsonicClient）

1. 系统：`ping`
2. 浏览：`getArtists`、`getArtist`、`getAlbum`、`getAlbumList2`
3. 搜索：`search3`
4. 媒体：`stream`、`getCoverArt`
5. 播放列表：`getPlaylists`、`getPlaylist`、`createPlaylist`、`updatePlaylist`、`deletePlaylist`
6. 互动：`getStarred2`、`star`、`unstar`、`scrobble`
7. 扩展：`getRandomSongs`、`getLyricsBySongId`

### 8.2 数据模型

1. `Song`
2. `Album`
3. `Artist` / `ArtistDetail`
4. `Playlist`

### 8.3 错误模型建议

1. 保留 `SubsonicApiException` 作为底层异常。
2. 新增统一 `Result<T, AppError>` 抽象（Phase 2）。
3. 错误分层：网络错误、认证错误、业务错误、解析错误。

## 9. 非功能需求

### 9.1 性能

1. 冷启动到可交互 < 2.5 秒（中端设备）。
2. 首屏列表渲染帧率目标 55 FPS+。
3. 常规操作主线程无明显卡顿（>100ms）。

### 9.2 稳定性

1. 音频播放链路异常可恢复，不导致应用崩溃。
2. 网络请求支持超时、重试与取消。
3. Provider 生命周期管理避免资源泄漏。

### 9.3 安全与隐私

1. 不在日志打印明文密码与完整 token。
2. 凭据本地存储已升级到安全存储（`flutter_secure_storage`），后续可继续补充更细粒度的数据隔离策略。
3. 网络层支持 HTTPS，HTTP 使用时提示风险。

### 9.4 可维护性

1. 模块边界保持四层架构：UI、State、Service、Data。
2. 核心模块单测覆盖率目标 ≥ 70%（Service/Data）。
3. 关键流程具备最小集成测试（登录、播放、搜索）。

### 9.5 可访问性

1. 控件可达性标签（语义化）覆盖核心页面。
2. 文本对比度满足 WCAG AA。
3. 关键操作支持键盘与读屏。

## 12. 风险与缓解

1. 风险：不同 Subsonic 服务实现差异导致兼容问题。  
   缓解：增加兼容分支与降级逻辑，构建兼容性测试样本。

2. 风险：后台播放在不同平台行为不一致。  
   缓解：建立平台特定测试清单，优先稳定基础媒体控制。

3. 风险：离线能力引入后复杂度显著上升。  
   缓解：先做“只读离线播放”，再扩展同步与冲突策略。

4. 风险：凭据安全要求提升。  
   缓解：分阶段迁移到安全存储，提供兼容迁移脚本。
